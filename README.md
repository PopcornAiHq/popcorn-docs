# Popcorn docs

Source for **[docs.popcorn.ai](https://docs.popcorn.ai)** — the concepts an
agent or a person needs to author, publish and operate a Popcorn app bundle.

This repository is **public**. See `CLAUDE.md` before writing anything.

## What the site serves

Every page exists twice, at stable paths: Markdown for an agent and HTML for a
browser. The agent-facing files sit at the root.

| Path | For |
|---|---|
| `/` | the landing page — guides, then every concept with its summary |
| `/llms.txt` | the index: every title, URL and summary, cheap enough to fetch whole |
| `/llms-full.txt` | every page body, concatenated |
| `/chunks.json` | one record per page — what the MCP server reads |
| `/<section>/<id>.md` | one page as Markdown |
| `/<section>/<id>.html` | the same page for a person |

## Layout

```
content/
├── _frontmatter.md   the contract every page's frontmatter follows
├── concepts/         one addressable idea per file — the unit an agent retrieves
└── guides/           task-shaped walkthroughs
evals/
└── questions.yaml    the validation set for the concept summaries
scripts/              build, checks and publish — python3 only, no dependencies
server/               the docs MCP server over build/chunks.json
build/                GENERATED by scripts/emit.py — gitignored, never edited
```

`INFORMATION-ARCHITECTURE.md` decides which directory a borderline page
belongs in.

## The summary is the product

Every page's frontmatter carries a `summary` under 400 characters. That field
is what an agent gets back in one call; the body is what the website and a CLI
checkout get. Writing the summary well is the work — a generator cannot do it,
and a body without one is not finished.

## Working on it

Everything runs on a bare `python3`. After any change under `content/`:

```bash
python3 scripts/check-content.py     # frontmatter contract
python3 scripts/emit.py              # rebuild build/ from empty
python3 scripts/check-links.py       # every advertised URL and page link resolves
python3 scripts/check-retrieval.py   # every eval question surfaces its concept
./scripts/check-public-repo.sh       # no internal references — reads the STAGED tree
```

`emit.py` must run before the two checks that read `build/`. The leak guard is
also the pre-commit hook, and it scans what is staged, so a fix it has not seen
yet needs a `git add` before it passes. To see the site, serve the build:

```bash
python3 -m http.server -d build 8000   # http://localhost:8000
```

CI runs the same five on every push and pull request; the content and leak
checks are required to merge.

## Publishing

A merge to `main` that touches `content/`, `scripts/` or the publish workflow
publishes the site: `.github/workflows/publish.yml` reruns the checks, uploads
`build/`, invalidates the CDN and then reads the live site back with
`scripts/check-published.py`. Nothing needs to be run by hand.

## Validating the summaries

`scripts/eval-kit.py` prints what a manual validation pass needs: the prompt
(`--prompt`), the questions (`--ask`) and a scoring sheet (`--sheet`). Run it
per assistant, one question per fresh session; the reasons are in
`evals/questions.yaml`. Write the sheet outside this repository — never into
`build/`, which is published whole.
